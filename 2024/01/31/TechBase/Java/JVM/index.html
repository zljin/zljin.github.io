Java虚拟机

Created2024-01-31|Updated2026-08-08|Java
|Post Views:

JVM 是实现 Java 跨平台的核心：javac 将 .java 源码编译为 .class 字节码，JVM 负责将字节码解释/编译为特定平台的机器码并执行，从而实现“一次编译，到处运行”。

一、JVM 内存模型

JVM 运行时数据区分为线程共享区和线程独占区：

线程共享区

区域 存储内容 异常情况
方法区 类信息、常量、静态变量、即时编译器（JIT）编译后的代码缓存等。JDK8 后由元空间（Metaspace）实现，使用本地内存。 若无法满足分配需求会抛出 OutOfMemoryError（元空间不足）
堆（Heap） 所有对象实例和数组，是 GC 管理的主要区域。 无法分配对象时抛出 OutOfMemoryError: Java heap space

线程独占区

区域 作用与特点 可能异常
虚拟机栈 每个 Java 方法执行时创建一个栈帧，存放局部变量表、操作数栈、动态链接、方法返回地址等。 栈深度超过限制 → StackOverflowError；无法扩展栈空间 → OutOfMemoryError
程序计数器 当前线程所执行的字节码行号指示器（分支、循环、跳转等依赖它）。 唯一不会抛出 OutOfMemoryError 的区域
本地方法栈 为 JVM 使用到的 Native 方法（C/C++ 实现）服务，类似虚拟机栈。 StackOverflowError / OutOfMemoryError

2.2 调优原则与场景

基本思路：

  1. 优先从代码和架构层面优化，确实无优化空间后再调整 JVM 参数；
  2. 通常在吞吐量、延迟、内存占用三个维度中进行权衡，选择两个重点优化。

需要调优的典型表现：

  • 频繁发生 Full GC（如一天多次或短间隔）
  • 老年代使用率持续上涨，直到达到设置的最大内存值
  • GC 停顿（Stop-The-World）时间过长（如超过 1 秒）
  • 出现 OutOfMemoryError
  • 应用 CPU 或内存使用异常偏高

调优关注点：

  • 吞吐量：用户代码执行时间 /（用户代码执行时间 + GC 时间）
  • 低延迟：缩短 STW 时间，提高响应速度
  • GC 算法选择：根据业务场景选择吞吐量优先或低延迟优先
  • 减少 Full GC，尽量让对象在 Minor GC 时被回收
  • 堆大小调整的依据：统计 Minor GC 的频率、耗时，Full GC 的最长持续时间及最坏频率，再结合业务重新设计各区域大小。

三、堆内存分代机制

3.1 对象生命周期

  1. 新建对象 → Eden 区分配内存。
  2. 发生 Minor GC，存活对象通过复制算法移动到 Survivor 区（S0 或 S1），年龄 +1。
  3. 对象在 Survivor 区每熬过一次 Minor GC，年龄 +1，直到达到 -XX:MaxTenuringThreshold（默认 15），晋升到老年代。
  4. 老年代空间不足时触发 Full GC（通常采用标记-整理算法）。

3.2 分代优势

  • 提升 GC 效率：针对不同代特点使用不同的回收算法和触发频率。
  • 控制停顿时间：通过调节新生代/老年代比例和 Survivor 区大小，可降低 Minor GC 频率，改善服务响应延迟。

3.3 监控示例

使用 jstat -gc <pid> 1000 10 实时监控 GC 状态（每秒打印一次，共 10 次），输出解读：

指标 含义
S0U/S1U Survivor 区使用量
EC/EU Eden 区容量 / 使用量
OC/OU 老年代容量 / 使用量
YGC Young GC 次数
YGCT Young GC 总耗时 (s)
FGC Full GC 次数
FGCT Full GC 总耗时 (s)

理想状态：

  • Survivor 区使用率 ≈ 60%～80%，充分利用且不溢出；
  • Minor GC 间隔 > 1 分钟；
  • Full GC 间隔 > 24 小时（或极少发生）。

四、类加载与双亲委派机制

4.1 类加载生命周期

  1. 加载：查找字节码并生成 Class 对象。
  2. 连接：
    • 验证：确保字节码安全；
    • 准备：为静态变量分配内存并赋零值；
    • 解析：符号引用 → 直接引用。
  3. 初始化：执行 <clinit>()，初始化静态变量和静态代码块。
  4. 使用：实例化或访问静态成员。
  5. 卸载：类被 GC 回收。

4.2 双亲委派模型

工作流程：
一个类加载器收到加载请求时，首先委托给父加载器，层层向上，直到启动类加载器。只有当父加载器无法找到该类（抛出 ClassNotFoundException）时，子加载器才尝试自己加载。

意义：

  • 安全：防止核心 API 被篡改。例如自定义的 java.lang.String 不会被加载，保证核心库纯净。
  • 唯一性：同一个类（全限定名 + 类加载器）只加载一次，避免重复加载。
  • 稳定性：避免类冲突导致的系统崩溃。

五、垃圾回收

Stop-The-World (STW)：GC 执行时，所有应用线程必须暂停，直到本次回收完成。

5.1 判断对象可回收的标准

(1) 引用计数法

为对象添加引用计数器，引用数为 0 即可回收。缺点：无法解决循环引用问题，Java 未采用此方法。

(2) 可达性分析

以一系列 GC Roots 为起点，搜索引用链，不可达的对象即为可回收。

可作 GC Roots 的对象：

  • 虚拟机栈（栈帧中的本地变量表）引用的对象
  • 方法区中静态属性和常量引用的对象
  • 本地方法栈中 JNI 引用的对象
  • 所有活跃线程

(3) 引用类型与回收策略

引用类型 回收时机 典型场景
强引用 永不回收，除非不再被引用 普通 new 出来的对象
软引用 内存不足时回收 缓存（SoftReference）
弱引用 下一次 GC 时回收 WeakHashMap
虚引用 随时可能回收，主要用于跟踪对象回收 直接内存管理

实战：将大型图像缓存从强引用改为软引用，内存紧张时自动释放不常用图片，避免 OOM，提升稳定性。

5.2 常用垃圾回收算法

算法 过程简介 特点 适用场景
标记-清除 标记存活对象，然后清除未标记对象 会产生内存碎片 老年代基础算法
复制 将存活对象复制到另一块区域，整体清理原区域 无碎片，但浪费空间；适合存活率低 新生代（Minor GC）
标记-整理 标记存活对象后，将所有存活对象向一端移动，清理边界外的内存 无碎片，但移动对象有开销 老年代
分代收集 组合使用上述算法，根据对象生命周期特点选择不同算法 综合效率高 当前 JVM 默认策略

5.3 垃圾回收器选择

GC 类型 适用硬件 特点
Serial GC 单 CPU、小内存 (<2G) 单线程，GC 时暂停所有应用线程
G1 GC 多 CPU、大内存 (>2G) 并发与并行，分代收集，空间整合，可预测停顿，注重低延迟，适合服务端应用

G1 特点：

  • 将堆划分为大小相等的 Region，不再物理隔离年轻代和老年代；
  • 以复制算法和标记-整理算法为主；
  • 可设定预期停顿时间（-XX:MaxGCPauseMillis）。

六、内存泄漏排查

6.1 常见原因

  1. 静态集合持有强引用：如 static List<Object>，对象无法回收，应及时清理或使用弱引用。
  2. 资源未关闭：如 IO 流、数据库连接，应使用 try-with-resources 自动关闭。
  3. ThreadLocal 未 remove：线程池中线程复用，导致 value 无法回收，使用后务必 remove()。
  4. 监听器/回调未注销：注册后未取消，对象持续被引用。
  5. 内部类持有外部类引用：非静态内部类或匿名内部类持有外部类引用，若内部类生命更长，则外部类无法回收。
  6. 缓存设计不合理：缓存无限增长，应设置容量上限或使用软/弱引用。

6.3 监控指标与告警阈值

通过 jstat -gc <pid> 1000 10 观察：

  • **老年代使用率 (OU/OC)**：

    • 85% → WARNING

    • 92% → CRITICAL

  • **元空间使用率 (MU/MC)**：

    • 90% → WARNING

    • 95% → CRITICAL

  • Full GC 次数：> 0 就需要调查原因
  • Young GC 单次耗时：> 200ms 需关注

排查原则：先解决容量问题（是否即将 OOM），再优化性能问题（GC 效率）。

七、CPU 过高排查

7.1 常见原因

代码层面：

  • 死循环、递归调用
  • 频繁 GC（内存不足导致）
  • 线程阻塞、死锁、资源竞争

系统层面：

  • 系统负载过高（其他进程抢占资源）
  • 物理内存不足，频繁交换
  • 磁盘 IO 或网络 IO 过高
  • 其他进程影响
